## Context

Currently, `InMemoryConnectionFactory` instantiates its own private `InMemoryBroker` state. This prevents connections created from different factory instances from sharing in-memory queues, which is a requirement for certain integration testing setups where factories are decoupled but target the same mock broker.

## Goals / Non-Goals

**Goals:**
- Add constructor support to `InMemoryConnectionFactory` allowing users to supply a `brokerId`.
- Implement `InMemoryBrokerRegistry` to manage, retrieve, and share `InMemoryBroker` instances in RAM by a string identifier.
- Retain default isolated behavior (creating a connection factory without a `brokerId` must automatically allocate a unique identifier and maintain broker isolation).
- Update the message ID generation strategy to use the active `brokerId` instead of always generating a timestamp hex prefix, unless the default constructor is used.
- Parse URI-like query parameters from queue names (e.g., `queueName?param=val`) in `InMemoryQueue`, separating the base name from a key-value map of parameters.

**Non-Goals:**
- No support for persistent registry storage (all registers are wiped when the JVM terminates).
- No dynamic re-binding of connections to a different broker after a connection is created.

## Decisions

### Decision 1: Shared Registry for In-Memory Brokers
- **Choice**: Implement a static registry `InMemoryBrokerRegistry` containing a `ConcurrentHashMap<String, InMemoryBroker>`.
- **Rationale**: A static concurrent registry provides thread-safe, global lookup of broker instances in RAM without requiring complex dependency injection patterns, aligning with a lightweight mock architecture.
- **Alternatives Considered**: Passing the broker instance around manually. Rejected because client applications interacting through the standard JMS `ConnectionFactory` interface cannot easily inject broker dependencies down to connections.

### Decision 2: Constructor Configuration in ConnectionFactory
- **Choice**: Extend `InMemoryConnectionFactory` with constructors `InMemoryConnectionFactory(String brokerId)`. The default no-arg constructor will delegate to `this(Long.toHexString(System.currentTimeMillis()).toLowerCase())`.
- **Rationale**: Keeps the codebase 100% backwards-compatible and retains isolation by default, while enabling explicit sharing with minimal configuration changes.

### Decision 3: Message ID Prefix Customization
- **Choice**: `InMemoryBroker` stores the assigned `brokerId` and tracks its instantiation number via a static atomic counter `instanceId`. It formats IDs generated by `generateNextMessageId()` as `ID:<brokerId>:<instanceId>:<sequence>`.
- **Rationale**: Ensures that message IDs remain unique, easily traceable, and contain instantiation markers. If a broker instance is destroyed and re-instantiated with the same `brokerId`, the `instanceId` increments, allowing detection of re-instantiation.

### Decision 4: Queue Name Query Parameter Parsing
- **Choice**: Parse queue names containing `?` inside `InMemoryQueue`. The portion before the `?` is treated as the queue name. The portion after the `?` is parsed by splitting key-value pairs separated by `&` and `=`, storing them in an unmodifiable `Map<String, String>` retrieved via `getParameters()`.
- **Rationale**: Keeps the broker destination mapping clean (since "myQueue?p=1" maps to the same broker queue as "myQueue"), while exposing metadata parameters to the calling application.

## Risks / Trade-offs

- **Risk**: Static registries can cause memory leaks in test runners if factories are created continuously with unique random IDs and never cleaned up.
  - **Mitigation**: The registry is lightweight, but we can also provide a registry cleanup method `InMemoryBrokerRegistry.clear()` if developers need to free memory between test runs.
